Homelab Project 1

Active Directory Attack and Detection Lab

Self-Hosted Lab · November 2026

Windows Server 2025 Wazuh 4.14.5 Kerberos Blue Team

Overview

I built a fully isolated Active Directory environment on Windows Server 2025, attacked it from a Kali Linux machine using real credential-based techniques, and built custom Wazuh detection rules that fire on live attack traffic. The goal was to understand both sides of the detection equation: what an attacker does and what that actually looks like in the logs.

Lab Architecture

DC01 — 192.168.100.50

Windows Server 2025, domain controller for corp.lab. Wazuh agent enrolled. Sysmon running with SwiftOnSecurity config.

Wazuh Manager — 192.168.100.10

Ubuntu Server. Wazuh 4.14.5 all-in-one (manager, indexer, dashboard). Central SIEM for the lab.

Kali-Attacker — 192.168.100.30

Kali Linux attacker, internal network only. No internet access by design. All tooling pre-installed.

Network

VirtualBox internal network (intnet). Air-gapped from the host's internet connection. 192.168.100.0/24.

The domain has five standard user accounts (jsmith, bjones, asilva, mkhan, twong) as spray targets, and one service account (svc_sql) with an MSSQLSvc SPN registered as the Kerberoasting target. Audit policy is configured on the Default Domain Controllers Policy to log Kerberos authentication (events 4768, 4769, 4771) and logon failures (4624, 4625). The DC01 Wazuh agent forwards both the Security log and Microsoft-Windows-Sysmon/Operational to the manager.

Attacks

Password Spray

A password spray tries one common password against every account in a list. The idea is to stay under account lockout thresholds while still covering a large number of targets. It is one of the most common initial access techniques against Active Directory environments because almost every large organization has at least one account with a weak or reused password.

I ran the spray from Kali using impacket's getTGT, which sends Kerberos AS-REQ packets directly to port 88 on the domain controller. Each failed attempt generates a Windows Security event 4771, which records the account name, source IP, and a failure code indicating wrong password. I used a password that none of the accounts had, so all five attempts failed.

for user in jsmith bjones asilva mkhan twong; do
  impacket-getTGT corp.lab/$user:WrongPass1 -dc-ip 192.168.100.50
done

Kerberoasting

Kerberoasting is a technique for extracting service account credentials from Active Directory without any special privileges. Any authenticated domain user can request a Kerberos service ticket for any account that has an SPN registered. The domain controller encrypts that ticket with the service account's password hash, and the attacker can take the ticket offline and crack it with a tool like Hashcat.

Windows Server 2025 disables RC4 at the KDC level by default, so the classic impacket-GetUserSPNs tool (which specifically requests RC4-encrypted tickets) fails regardless of account settings or group policy changes. I used impacket-getST instead, which lets the domain controller choose the encryption type. The 4769 event that the domain controller logs when it hands out a service ticket is what a blue team actually has to work with before the ticket leaves the network.

impacket-getST -spn MSSQLSvc/dc01.corp.lab:1433 \
  -dc-ip 192.168.100.50 corp.lab/jsmith:LabPass123!

Detection Rules

Both rules live in /var/ossec/etc/rules/local_rules.xml on the Wazuh manager. Rule IDs above 100000 are the custom range.

Rule 100100: Password Spray

Rule 100100 Level 10

Password spray: 5 or more authentication failures from the same source IP within 60 seconds.

The rule chains off built-in Wazuh rule 60104, which fires for every Windows audit failure event. A frequency counter watches for five or more of those events sharing the same win.eventdata.ipAddress value within a 60-second window. When the threshold is crossed, Wazuh raises a level 10 alert.

<rule id="100100" level="10" frequency="5" timeframe="60">
  <if_matched_sid>60104</if_matched_sid>
  <same_field>win.eventdata.ipAddress</same_field>
  <description>Password spray: 5+ authentication failures from same source in 60 seconds</description>
  <group>attack,credential_access</group>
</rule>

Rule 100101: Kerberoasting

Rule 100101 Level 12

Kerberoasting: service ticket requested for SQL service account.

This rule watches for event 4769 (Kerberos service ticket operations) where the service name matches svc_sql or MSSQLSvc and the status is success (0x0). The match is case-insensitive. A level 12 alert fires the moment the domain controller issues the ticket.

<rule id="100101" level="12">
  <if_group>windows</if_group>
  <field name="win.system.eventID">^4769$</field>
  <field name="win.eventdata.serviceName" type="pcre2">(?i)svc_sql|MSSQLSvc</field>
  <field name="win.eventdata.status">^0x0$</field>
  <description>Kerberoasting: service ticket requested for SQL service account</description>
  <group>attack,credential_access</group>
</rule>

Results

Both alerts appeared in the Wazuh Threat Hunting dashboard in real time during testing. Rule 100100 fired at level 10 within seconds of the spray completing. Rule 100101 fired at level 12 immediately after the getST command ran on Kali.

What I Learned

The hardest part of this project was not running the attacks. It was getting the detection logic right. The first version of the spray rule never fired even though the Windows Security log had all five 4771 events. The diagnosis took some work: I had to search the Wazuh archive and discover that the events were arriving at the SIEM but a pcre2 field matching attribute in the custom base rule was silently failing. The fix was to chain the frequency rule directly off the working built-in rule, which had already been tested against the actual event structure produced by this version of Windows.

The Kerberoasting side had a similar lesson. Windows Server 2025 enforces AES at the KDC and silently rejects RC4 ticket requests at multiple layers, even when you explicitly re-enable RC4 in group policy and the LSA registry. The classic impacket tool that every Kerberoasting tutorial uses just does not work against a modern DC without significant infrastructure changes. Pivoting to getST taught me that the operationally relevant observable for blue teams is the 4769 event itself, regardless of encryption type.

Sysmon is running on DC01 and forwarding to Wazuh, ready for host-based detection work in future projects.
